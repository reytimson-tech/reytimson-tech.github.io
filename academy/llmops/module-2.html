Evaluating LLM quality

If you can't measure quality, every change is a guess. This module shows how to build evaluations that make shipping safe.

Learning objectives

  • Write specific, measurable success criteria
  • Build representative, versioned evaluation sets
  • Choose between code, LLM and human grading
  • Implement an evaluation harness and regression gate
  • Combine offline and online evaluation

2.1 Start with success criteria

Anthropic's guidance on evaluations recommends defining criteria that are specific, measurable, achievable and relevant before you build. Not "good answers", but, for example: "on a held-out set of 500 real customer questions, at least 90% of answers are rated correct and grounded, with no answers revealing personal data, and median latency under 3 seconds."

2.2 Build an evaluation set

  • Representative: mirrors real inputs — sample from logs where lawful
  • Edge cases: empty, very long, ambiguous, off-topic, multilingual, adversarial
  • Labelled: expected answers, or rubrics describing a good answer
  • Versioned: stored with the code; grows as you find new failures
  • Separate: a held-out set you don't tune against

2.3 Three ways to grade

GraderExamplesStrengthsWeaknesses
CodeExact match, valid JSON, contains required field, regex, lengthFast, cheap, reliable, scalableCan't judge nuance
LLM judgeRubric-based scores for correctness, tone, groundednessScales to open-ended outputsMust be validated; can be biased
HumanExpert review, side-by-side preferenceHighest quality and flexibilitySlow and expensive

Use code where you can, LLM judges where you must (checked against human samples), and humans for calibration and high-stakes decisions.

2.4 An evaluation harness

Python · a minimal evaluation harnessimport json, re, statistics, time

def grade_code(case, output):
    checks = {
        "valid_json": _is_json(output),
        "mentions_required": all(w.lower() in output.lower() for w in case.get("must_include", [])),
        "no_forbidden": not any(w.lower() in output.lower() for w in case.get("must_not_include", [])),
    }
    return all(checks.values()), checks

def _is_json(s):
    try: json.loads(s); return True
    except ValueError: return False

def run_eval(cases, generate, version):
    results, latencies = [], []
    for case in cases:
        t0 = time.time()
        out = generate(case["input"])
        latencies.append(time.time() - t0)
        ok, detail = grade_code(case, out)
        results.append({"id": case["id"], "pass": ok, **detail})
    pass_rate = sum(r["pass"] for r in results) / len(results)
    print(f"{version}: pass rate {pass_rate:.1%}, median latency {statistics.median(latencies):.2f}s")
    return pass_rate, results

2.5 Evals as a release gate

Run the evaluation suite automatically whenever prompts, retrieval, tools or models change — for example in your CI pipeline — and block releases that fall below thresholds or regress against the current version.

2.6 Offline vs online evaluation

Offline evaluation uses your test set before release. Online evaluation measures behaviour with real users: thumbs up/down, edits, escalations, task completion, A/B tests. You need both — offline to prevent regressions, online to discover what your test set missed.

Key takeaways

  • Define SMART-style success criteria first.
  • Evaluation sets need real inputs, edge cases, labels and versioning.
  • Prefer code graders; validate LLM judges against humans.
  • Run evals automatically and block regressions.
  • Offline evals prevent regressions; online signals reveal gaps.
